# go-email-verification-protocol

> [!WARNING]
> As of Chrome 151, EVP is still opt-in. For production use, ensure that you are registered for the [origin trial](https://developer.chrome.com/origintrials/#/view_trial/10696049115004929). For local testing, enable the Chrome Developer Flag "Email Verification Protocol" (chrome://flags/#email-verification-protocol) 

A small Go verifier for the **Email Verification Protocol (EVP)**.

EVP allows a supported browser and email provider to prove that a user controls an email address without requiring your application to send a verification email, magic link, or one-time code.

This package handles the verifier-side protocol behind a small API:

```go
result, err := evp.Verify(ctx, token, evp.VerifyOptions{
    Email:    "user@gmail.com",
    Nonce:    nonce,
    Audience: "https://example.com",
})
```

If verification succeeds, the returned result contains the email address attested by the email provider:

```go
if err == nil && result.Verified {
    // Email ownership has been verified.
}
```

EVP should be treated as a **progressive enhancement**. If the browser does not provide a token, the email provider does not support EVP, or verification fails, your application can continue using its existing email verification flow.

## Installation

```bash
go get github.com/kvizdos/go-email-verification-protocol
```

```go
import evp "github.com/kvizdos/go-email-verification-protocol"
```

## Usage

Add the EVP token field alongside your email input:

```html
<input
    name="email"
    type="email"
    autocomplete="email">

<input
    name="email_verification_token"
    type="hidden"
    nonce="YOUR_SESSION_NONCE"
    autocomplete="email-verification-token">
```

The nonce should be generated by your application and associated with the verification attempt or user session.

When the form is submitted, pass the browser-provided token to `evp.Verify`:

```go
result, err := evp.Verify(
    r.Context(),
    r.FormValue("email_verification_token"),
    evp.VerifyOptions{
        Email:    r.FormValue("email"),
        Nonce:    expectedNonce,
        Audience: "https://example.com",
    },
)
if err != nil {
    // EVP verification did not succeed.
    // Fall back to your normal email verification flow.
    sendVerificationEmail()
    return
}

// EVP verification succeeded.
markEmailVerified(result.Email)
```

A successful call means the submitted proof has been cryptographically verified and bound to the expected email, nonce, and audience.

## Progressive enhancement

EVP is designed to sit in front of your existing email verification flow rather than replace it.

A typical integration is:

```go
if token != "" {
    result, err := evp.Verify(ctx, token, evp.VerifyOptions{
        Email:    email,
        Nonce:    nonce,
        Audience: origin,
    })

    if err == nil && result.Verified {
        markEmailVerified(result.Email)
        return
    }
}

sendVerificationEmail(email)
```

For users whose browser and email provider support EVP, verification can happen without the user leaving your application.

Everyone else continues through your existing verification flow.

## What `Verify` does

`evp.Verify` handles the verifier-side EVP flow, including:

1. Validating the expected email, nonce, audience, and token.
2. Resolving the email domain's `_email-verification` DNS record.
3. Determining the issuer authorized to attest addresses for that domain.
4. Parsing the submitted SD-JWT presentation and key-binding JWT.
5. Confirming the token's issuer matches the issuer authorized through DNS.
6. Discovering the issuer's `/.well-known/email-verification` configuration.
7. Resolving the issuer's signing keys from its JWKS.
8. Verifying the issuer-signed Email Verification Token.
9. Requiring the issuer's `email_verified` claim to be `true`.
10. Comparing the verified email address case-insensitively with the expected address.
11. Extracting the browser confirmation key from the issuer token.
12. Verifying the browser's key-binding JWT.
13. Validating the expected nonce and audience.
14. Validating the key-binding issuance time / maximum age.
15. Validating the SD-JWT `sd_hash` binding.

Applications therefore do not need to directly implement DNS discovery, issuer discovery, JWKS handling, JWT verification, SD-JWT parsing, or browser key binding.

## Verification result

On success, `Verify` returns an `evp.Result`:

```go
type Result struct {
    Verified     bool
    Email        string
    Issuer       string
    PrivateEmail bool
}
```

For example:

```go
result, err := evp.Verify(ctx, token, opts)
if err != nil {
    // Verification failed.
    return
}

fmt.Println(result.Verified)
fmt.Println(result.Email)
fmt.Println(result.Issuer)
fmt.Println(result.PrivateEmail)
```

A `nil` error indicates that EVP verification succeeded.

## Errors

`Verify` exposes errors that can be inspected with `errors.Is`:

```go
result, err := evp.Verify(ctx, token, opts)
if err != nil {
    switch {
    case errors.Is(err, evp.ErrIssuerResolution):
        // The email domain could not be resolved to an EVP issuer.
        // Usually safe to fall back to normal email verification.

    case errors.Is(err, evp.ErrEmailNotVerified):
        // The provider did not attest this email as verified.
        // Fall back to normal email verification.

    case errors.Is(err, evp.ErrTokenExpired):
        // The EVP proof is too old.
        // Retry or fall back to normal email verification.

    case errors.Is(err, evp.ErrNonceMismatch):
        // The proof is not bound to the expected verification attempt.
        // Reject it and restart/fall back.

    default:
        // Invalid, untrusted, or otherwise unusable EVP proof.
        log.Printf("EVP verification failed: %v", err)
    }

    return
}

// Verified.
_ = result
```

### Errors applications may want to handle

The following errors are particularly useful when deciding how to continue the user flow:

| Error | Meaning | Typical action |
|---|---|---|
| `ErrIssuerResolution` | No usable EVP issuer could be resolved for the email domain | Fall back |
| `ErrEmailNotVerified` | Provider did not attest the email as verified | Fall back |
| `ErrTokenExpired` | The proof exceeded its allowed lifetime | Retry or fall back |
| `ErrNonceMismatch` | Proof belongs to a different verification attempt | Reject and retry/fall back |
| `ErrEmailMismatch` | Provider verified a different email address | Reject; consider logging |
| `ErrAudienceMismatch` | Proof was issued for a different audience | Reject; consider logging |
| `ErrInvalidInput` | Required arguments to `Verify` are missing or invalid | Application/integration error |

### Other verification errors

The package also exposes:

```go
evp.ErrIssuerDiscovery
evp.ErrUnauthorizedIssuer
evp.ErrMalformedToken
evp.ErrInvalidIssuerToken
evp.ErrInvalidKeyBinding
```

Applications generally do not need separate user-facing behavior for each of these.

They mean the EVP proof could not be trusted or completed. The application should reject the proof, optionally log the underlying error for diagnostics, and fall back to its normal email verification mechanism.

EVP verification errors generally should **not** be displayed directly to users.

## `VerifyOptions`

Verification is controlled by `evp.VerifyOptions`:

```go
type VerifyOptions struct {
    Email    string
    Nonce    string
    Audience string

    // Maximum permitted age of the browser key-binding proof.
    MaxAge time.Duration

   	EVTMaxAge time.Duration
}
```

### Email

The email address your application expects the provider to have verified:

```go
Email: "user@gmail.com"
```

The verified email returned by the issuer is compared case-insensitively with this value.

### Nonce

The nonce associated with the current verification attempt:

```go
Nonce: nonce
```

The same value must be provided to the browser through the EVP form field and supplied to `Verify`.

A token containing a different nonce is rejected.

### Audience

The relying-party origin expected in the browser's key-binding proof:

```go
Audience: "https://example.com"
```

A proof issued for another audience is rejected.

### MaxAge

The maximum permitted age of the key-binding proof:

```go
MaxAge: 5 * time.Minute
```

This provides a bounded replay window for EVP proofs.

## Security model

A successful `evp.Verify` does more than decode a token.

The verification chain is approximately:

```text
Email address
     │
     ▼
_email-verification.<email-domain>
     │
     ▼
Authorized issuer
     │
     ▼
Issuer discovery
     │
     ▼
Issuer JWKS
     │
     ▼
Issuer-signed Email Verification Token
     │
     ├── email
     ├── email_verified
     └── browser confirmation key
              │
              ▼
        Key Binding JWT
              │
              ├── audience
              ├── nonce
              ├── issued-at
              └── sd_hash
```

`Verify` succeeds only when the relevant pieces of that chain validate.

Do not treat an EVP token as verified by simply decoding its JWT claims.

## Protocol status

The Email Verification Protocol and its browser implementations are still evolving.

Breaking changes may occur while the proposal and browser implementations are under development.

This library aims to absorb those protocol details while keeping the application-facing API approximately:

```go
evp.Verify(ctx, token, options)
```

Applications should nevertheless continue to maintain a normal email verification fallback.

## Scope

This package currently implements the **relying-party / verifier side** of EVP.

Its primary purpose is:

```go
result, err := evp.Verify(...)
```

It does not currently provide an implementation for email providers issuing EVP proofs.
