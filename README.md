# go-email-verification-protocol

> [!WARNING]
> The Email Verification Protocol (EVP) and browser implementations are still evolving. As of the current Chrome origin-trial implementation, EVP remains opt-in. Keep your normal email-verification flow available as a fallback.

A Go verifier for the **Email Verification Protocol (EVP)**.

EVP allows a supported browser and email provider to prove that a user controls an email address without requiring your application to send a verification email, magic link, or one-time code.

This package implements the **relying-party / verifier side** of the protocol behind a small application-facing API:

```go
result, err := evp.Verify(ctx, token, evp.VerifyOptions{
    Email:     email,
    Nonce:     nonce,
    Audience:  "https://example.com",
    EVTMaxAge: 5 * time.Minute,
    KBMaxAge:  5 * time.Minute,
})
```

If verification succeeds, the returned result contains the email address attested by the issuer:

```go
if err == nil && result.Verified {
    markEmailVerified(result.Email)
}
```

EVP should be treated as a **progressive enhancement**. If the browser does not provide an EVP token, the email provider does not support EVP, or verification fails, continue through your existing email-verification flow.

## Installation

```bash
go get github.com/kvizdos/go-email-verification-protocol
```

```go
import evp "github.com/kvizdos/go-email-verification-protocol"
```

## Basic usage

### 1. Add the EVP fields to your form

```html
<input
    name="email"
    type="email"
    autocomplete="email">

<input
    name="email_verification_token"
    type="hidden"
    nonce="YOUR_SESSION_NONCE"
    autocomplete="email-verification-token">
```

The nonce must be generated by your application and bound to the verification attempt or browser session.

Use a cryptographically random nonce with at least 128 bits of entropy, make it unique per verification request, and keep it valid only for a limited time.

### 2. Verify the submitted token

```go
package handlers

import (
    "context"
    "net/http"
    "time"

    evp "github.com/kvizdos/go-email-verification-protocol"
)

func handleSignup(w http.ResponseWriter, r *http.Request) {
    email := r.FormValue("email")
    token := r.FormValue("email_verification_token")

    // Load the nonce that your application previously generated
    // and bound to this verification attempt/session.
    expectedNonce := loadExpectedNonce(r)

    // The audience is the relying-party origin.
    origin := "https://example.com"

    // Give the entire verification flow a deadline.
    ctx, cancel := context.WithTimeout(
        r.Context(),
        15*time.Second,
    )
    defer cancel()

    result, err := evp.Verify(
        ctx,
        token,
        evp.VerifyOptions{
            Email:     email,
            Nonce:     expectedNonce,
            Audience:  origin,
            EVTMaxAge: 5 * time.Minute,
            KBMaxAge:  5 * time.Minute,
        },
    )

    if err != nil {
        // EVP was unavailable, invalid, expired, unsupported,
        // or otherwise could not be trusted.
        //
        // Fall back to your normal email-verification flow.
        sendVerificationEmail(email)
        return
    }

    if result.Verified {
        markEmailVerified(result.Email)
    }
}
```

A successful call means the submitted proof has been cryptographically verified and bound to the expected:

- email address
- issuer authorized through DNS
- browser confirmation key
- relying-party origin
- nonce
- EVT issuance time
- key-binding issuance time
- SD-JWT hash binding

## Progressive enhancement

EVP is designed to sit in front of your normal verification flow rather than replace it.

A typical integration looks like:

```go
if token != "" {
    result, err := evp.Verify(ctx, token, evp.VerifyOptions{
        Email:     email,
        Nonce:     nonce,
        Audience:  origin,
        EVTMaxAge: 5 * time.Minute,
        KBMaxAge:  5 * time.Minute,
    })

    if err == nil && result.Verified {
        markEmailVerified(result.Email)
        return
    }
}

sendVerificationEmail(email)
```

Supported users can complete verification without leaving your application.

Everyone else continues through the same verification flow you already use.

## `VerifyOptions`

Verification is controlled by `evp.VerifyOptions`:

```go
type VerifyOptions struct {
    Email     string
    Nonce     string
    Audience  string
    EVTMaxAge time.Duration
    KBMaxAge  time.Duration
}
```

### `Email`

The email address your application expects the issuer to have verified.

```go
Email: "user@gmail.com"
```

The verified `email` claim is compared case-insensitively with this value.

### `Nonce`

The nonce bound to the current verification attempt.

```go
Nonce: expectedNonce
```

The same nonce must be provided to the browser through the EVP form field and supplied to `Verify`.

A proof containing another nonce is rejected.

Your application is responsible for nonce lifecycle:

- generate it with a cryptographically secure random source
- use at least 128 bits of entropy
- bind it to the browser session or verification attempt
- make it unique per verification request
- expire it after a limited period
- preferably consume it after successful verification

### `Audience`

The relying-party origin expected in the browser key-binding proof.

```go
Audience: "https://example.com"
```

A proof issued for another audience is rejected.

Use the origin, not an arbitrary page URL:

```text
https://example.com
```

not:

```text
https://example.com/signup?step=2
```

### `EVTMaxAge`

The maximum permitted age of the issuer-signed **Email Verification Token (EVT)**.

```go
EVTMaxAge: 5 * time.Minute
```

This is checked against the EVT's `iat` claim.

### `KBMaxAge`

The maximum permitted age of the browser-created **Key Binding JWT (KB-JWT)**.

```go
KBMaxAge: 5 * time.Minute
```

This is checked independently against the KB-JWT's `iat` claim.

The EVT and KB-JWT are created at different points in the protocol, so their freshness windows are intentionally configured separately.

> [!IMPORTANT]
> Set both `EVTMaxAge` and `KBMaxAge` to non-zero values. A relying party should always enforce a bounded freshness window for both proofs.

## What `Verify` does

`evp.Verify` performs the verifier-side EVP chain:

1. Validates the expected token, email, nonce, and audience.
2. Extracts the email domain.
3. Resolves `_email-verification.<email-domain>` through DNS TXT.
4. Determines the issuer authorized by that email domain.
5. Parses the submitted EVT + key-binding presentation.
6. Reads the unverified EVT issuer only to identify which issuer must be authorized.
7. Canonicalizes the DNS issuer and EVT issuer for comparison.
8. Rejects the token if its issuer is not the issuer authorized through DNS.
9. Fetches the issuer's `/.well-known/email-verification` metadata.
10. Validates the issuer's advertised signing algorithms.
11. Resolves the issuer's JWKS.
12. Cryptographically verifies the issuer-signed EVT.
13. Validates the EVT issuance time.
14. Requires `email_verified=true`.
15. Requires the verified email to match the expected email.
16. Extracts the browser confirmation key from `cnf.jwk`.
17. Verifies the KB-JWT signature with that confirmation key.
18. Verifies the relying-party audience.
19. Verifies the session nonce.
20. Verifies the KB-JWT issuance time.
21. Verifies the SD-JWT `sd_hash` binding.

Applications therefore do not need to directly implement DNS issuer discovery, `.well-known` discovery, JWKS handling, issuer JWT validation, browser key binding, or SD-JWT hash verification.

## Issuer identity compatibility

The current EVP draft represents the issuer identifier as a host such as:

```text
issuer.example
```

Current Chrome/Gmail deployments may use an EVT `iss` value containing the HTTPS scheme:

```text
https://accounts.google.com
```

while DNS delegation returns:

```text
iss=accounts.google.com
```

The verifier canonicalizes both representations before comparing them, so both forms resolve to the same issuer identity:

```text
accounts.google.com
```

HTTPS is still required for issuer discovery.

## Verification result

On success, `Verify` returns an `evp.Result`:

```go
type Result struct {
    Verified     bool
    Email        string
    Issuer       string
    PrivateEmail bool
}
```

Example:

```go
result, err := evp.Verify(ctx, token, opts)
if err != nil {
    return
}

fmt.Println(result.Verified)
fmt.Println(result.Email)
fmt.Println(result.Issuer)
fmt.Println(result.PrivateEmail)
```

A `nil` error indicates that EVP verification succeeded.

`Issuer` is the issuer value from the cryptographically verified EVT.

`PrivateEmail` surfaces the EVT's `is_private_email` claim when present.

> [!NOTE]
> The current verifier still requires the verified EVT email to match `VerifyOptions.Email`. Applications that want a flow where a private relay address intentionally differs from the originally entered address will need application-level handling beyond the current API.

## Errors

`Verify` exposes errors that can be inspected with `errors.Is`:

```go
result, err := evp.Verify(ctx, token, opts)
if err != nil {
    switch {
    case errors.Is(err, evp.ErrIssuerResolution):
        // No usable issuer could be resolved for the email domain.
        // Usually safe to fall back.

    case errors.Is(err, evp.ErrIssuerDiscovery):
        // Issuer metadata or signing keys could not be loaded.
        // Usually safe to fall back.

    case errors.Is(err, evp.ErrUnauthorizedIssuer):
        // The EVT issuer is not authorized by the email domain.
        // Reject the EVP proof.

    case errors.Is(err, evp.ErrEmailNotVerified):
        // The issuer did not attest email_verified=true.
        // Fall back.

    case errors.Is(err, evp.ErrEmailMismatch):
        // The issuer verified another email address.
        // Reject the proof.

    case errors.Is(err, evp.ErrTokenExpired):
        // The proof exceeded the configured freshness window.
        // Retry or fall back.

    case errors.Is(err, evp.ErrNonceMismatch):
        // The proof belongs to another verification attempt.
        // Reject and restart/fall back.

    case errors.Is(err, evp.ErrAudienceMismatch):
        // The proof was bound to another RP origin.
        // Reject.

    default:
        // Invalid, malformed, cryptographically invalid,
        // or otherwise unusable EVP proof.
        log.Printf("EVP verification failed: %v", err)
    }

    return
}

_ = result
```

### Common errors

| Error | Meaning | Typical action |
|---|---|---|
| `ErrInvalidInput` | Required verification input is missing or invalid | Fix the integration |
| `ErrIssuerResolution` | No usable EVP issuer could be resolved for the email domain | Fall back |
| `ErrIssuerDiscovery` | Issuer metadata or keys could not be loaded | Fall back |
| `ErrUnauthorizedIssuer` | EVT issuer does not match the issuer authorized through DNS | Reject |
| `ErrMalformedToken` | Submitted EVP presentation could not be parsed | Reject / fall back |
| `ErrInvalidIssuerToken` | Issuer-signed EVT could not be trusted | Reject |
| `ErrEmailNotVerified` | Issuer did not assert `email_verified=true` | Fall back |
| `ErrEmailMismatch` | Verified email differs from the expected email | Reject |
| `ErrInvalidKeyBinding` | Browser key-binding proof is invalid | Reject |
| `ErrNonceMismatch` | Proof is bound to another verification attempt | Reject |
| `ErrAudienceMismatch` | Proof is bound to another RP origin | Reject |
| `ErrTokenExpired` | EVT or KB-JWT exceeded the configured freshness window | Retry / fall back |
| `ErrInvalidPresentation` | SD-JWT / key-binding relationship is invalid | Reject |

Verification errors generally should **not** be shown directly to end users.

## Network and resource hardening

Issuer discovery requires outbound DNS and HTTPS requests based on the email domain being verified.

The default issuer resolver includes defensive controls around those operations.

### Outbound HTTP restrictions

Issuer-discovery and JWKS requests:

- require HTTPS
- reject user-info URLs
- reject loopback destinations
- reject private-network destinations
- reject link-local destinations
- reject unspecified and multicast destinations
- validate redirect destinations
- limit redirect chains
- avoid environment-configured proxy bypasses
- resolve and validate destination IPs before dialing them

These checks are intended to reduce SSRF and DNS-rebinding risk.

### Response-size limits

Issuer metadata responses are bounded before JSON decoding.

JWKS responses are also fetched through the hardened HTTP client and should be bounded before the downstream JWKS decoder consumes the body.

### Caching and concurrency

The resolver caches:

- email-domain → authorized issuer lookups
- issuer → `.well-known/email-verification` configuration
- JWKS key functions

Caches are bounded and stale entries are evicted.

In-flight loads for the same resource are deduplicated, and fresh outbound DNS/discovery/JWKS work is concurrency-limited to reduce attacker-controlled outbound work.

### Caller-side rate limiting is still required

Library-level caching and concurrency limits do **not** replace normal abuse protection on your public endpoint.

An attacker can rotate email domains or issuer hosts to intentionally create cache misses.

Applications should rate-limit the endpoint that calls `evp.Verify`, typically per IP address, session, account, or another application-appropriate abuse signal.

## Context and timeouts

`Verify` accepts a `context.Context`, and callers should provide a sensible deadline for the complete verification operation:

```go
ctx, cancel := context.WithTimeout(
    r.Context(),
    15*time.Second,
)
defer cancel()

result, err := evp.Verify(ctx, token, opts)
```

This gives DNS resolution, issuer discovery, and the rest of the verification pipeline a common cancellation boundary.

## Chrome compatibility note: EVT `kid`

The current EVP draft requires the EVT JOSE header to contain a `kid`.

Current Chrome/Gmail EVP behavior has been observed to omit `kid` from the EVT header.

For interoperability with that implementation, this library currently does **not** strictly require `kid` when verifying the EVT.

Issuer signature verification is still required and is performed against the issuer's authorized JWKS.

This is an intentional compatibility exception while browser implementations and the draft continue to evolve.

## Security model

A successful `evp.Verify` does more than decode a JWT.

The trust chain is approximately:

```text
Expected email
     │
     ▼
_email-verification.<email-domain>
     │
     ▼
Authorized issuer
     │
     ├── canonical issuer identity
     │
     ▼
https://<issuer>/.well-known/email-verification
     │
     ▼
Issuer JWKS
     │
     ▼
Issuer-signed EVT
     │
     ├── iss
     ├── iat
     ├── email
     ├── email_verified
     └── cnf.jwk
             │
             ▼
        Browser KB-JWT
             │
             ├── aud
             ├── nonce
             ├── iat
             └── sd_hash
```

`Verify` succeeds only when the relevant pieces of this chain validate.

Do **not** treat an EVP token as verified by simply base64-decoding its JWT claims.

## Nonce security

The nonce is a critical part of session binding.

Applications should generate the nonce using `crypto/rand`.

For example:

```go
package verification

import (
    "crypto/rand"
    "encoding/base64"
)

func generateNonce() (string, error) {
    b := make([]byte, 32)

    if _, err := rand.Read(b); err != nil {
        return "", err
    }

    return base64.RawURLEncoding.EncodeToString(b), nil
}
```

That produces a 256-bit nonce.

Store it server-side or otherwise bind it securely to the verification attempt, then compare against the exact nonce supplied to `evp.Verify`.

## Operational recommendations

For a production relying party:

- keep your normal email-verification fallback
- set both `EVTMaxAge` and `KBMaxAge`
- use a request context with a deadline
- generate a fresh session-bound nonce per verification attempt
- expire or consume successful nonces
- rate-limit the endpoint calling `Verify`
- do not expose raw verification errors directly to users
- log suspicious issuer, audience, nonce, or signature failures for diagnostics
- keep this dependency up to date while EVP is still evolving

## Scope

This package currently implements the **relying-party / verifier side** of EVP.

Its primary API is:

```go
result, err := evp.Verify(ctx, token, options)
```

It does not provide an email-provider / EVP issuer implementation.

## Protocol status

The Email Verification Protocol is still under development and browser implementations may differ from the current IETF draft.

This library intentionally contains compatibility behavior for real browser implementations where necessary, while keeping the application-facing API small.

Applications should continue to maintain a normal verification fallback.
